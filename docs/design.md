# toss/es-toolkit Skill `es-toolkit:migrate` 평가 설계 (프로젝트 단위)

이 문서는 실행 전에 고정하는 설계다. 반복 횟수 K와 시간·턴 한도는 정하는 규칙만 적고, 값은 사전 등록 파일에 넣는다.

용어: **Skill**은 toss/es-toolkit 저장소의 Claude Code 플러그인에 들어 있는 `es-toolkit:migrate`(`es-toolkit-plugin/skills/migrate/SKILL.md`, blob `3a83c14`)를 가리킨다. **es-toolkit**은 같은 저장소의 라이브러리를 가리킨다.

## 1. Skill이 쓰이는 상황과 목적

| 출처                                   | 내용                                                                                                                                                                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SKILL.md` description                 | lodash에서 옮겨 가려 할 때, lodash import를 바꾸려 할 때, es-toolkit으로 바꿔 번들을 줄이려 할 때, strict와 compat의 차이를 알고 싶을 때 쓴다.                                          |
| 플러그인 README                        | `migrate`는 lodash 코드를 es-toolkit으로 전환하도록 안내하고 strict와 compat API의 차이를 이해시킨다. 사용 예에 "convert all lodash imports in this file", "migration strategy"가 있다. |
| es-toolkit 문서 `docs/compat/intro.md` | compat은 이미 lodash를 쓰는 코드베이스를 호출부 수정 없이 옮기려고 있다. 권장 순서는 import를 compat으로 바꾼 뒤 시간을 두고 strict로 옮기는 것이다.                                    |
| `SKILL.md` 전략 절                     | Option B "compat을 거친 점진 전환"을 대규모 코드베이스용으로 소개하고 레거시에 권장한다.                                                                                                |

Skill이 쓰이는 상황은 **이미 lodash를 쓰는 기존 프로젝트를 es-toolkit으로 옮기는 일**이다. 이 평가에서 Skill의 목적은 다음 하나로 정의한다.

> **프로젝트 전체에서 lodash를 es-toolkit으로 빠짐없이 바꾸고, 기존 동작을 유지한다.**

진입점(strict, compat, 네이티브 코드)은 채점하지 않는다. es-toolkit 문서와 Skill이 모두 compat을 먼저 쓰는 방식을 권하므로, 동작을 지키는 한 어느 진입점도 정답이다. strict와 compat의 차이를 제대로 판단했는지는 동작이 갈리는 지점을 겨냥한 숨김 검사(5.2)에서 드러난다.

번들 크기와 실행 비용은 부차 지표로 보고하고 판정하지 않는다.

## 2. 시험 프로젝트

lodash에서 es-toolkit으로 바꾸는 PR을 실제로 머지한 오픈소스 프로젝트를, 그 PR 직전 커밋으로 되돌려 쓴다.

| 프로젝트                       | 소유·규모        | 전환 PR | 직전 커밋 | lodash 사용                                                                                |
| ------------------------------ | ---------------- | ------- | --------- | ------------------------------------------------------------------------------------------ |
| recharts/recharts              | 조직, 스타 27.7k | #5811   | `a28c686` | src 24파일, `lodash/x` import 32개, 17종. 테스트에서 `uniqueId`                            |
| acacode/swagger-typescript-api | 조직, 스타 4.1k  | #1562   | PR의 base | src 19파일 `import lodash from "lodash"` 127회 25종, 템플릿 11개가 `_` 69회, 공개 타입 1곳 |

고른 기준은 다음과 같다. 널리 쓰이는 조직 저장소이고, 사람이 머지한 전환 PR이 있고, 자체 테스트가 오프라인에서 돌고, 에이전트가 한 번에 다룰 수 있는 크기다. commitlint(#4734)는 전환 범위가 작고(소스 4파일), 전환 대상 패키지의 테스트 4개가 Windows 심볼릭 링크 권한 때문에 원래 커밋에서부터 실패해서 뺐다. Storybook과 CKEditor 5는 저장소가 커서 실행마다 설치와 테스트를 할 수 없어 뺐다.

시험 환경(fixture)은 직전 커밋의 작업 트리, 설치된 `node_modules`, 미리 넣은 es-toolkit 1.53.2로 구성한다. es-toolkit은 `package.json`에 선언하지 않은 상태로 둔다. 실행 중에는 네트워크가 막혀 있어 에이전트가 패키지를 설치할 수 없기 때문이다.

## 3. 실험 조건과 모델

| 조건     | 에이전트에게 주는 것                                                                                                                                                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| baseline | 지시문만 준다. 플러그인을 넣지 않는다.                                                                                                                                                                                                                    |
| skill    | 지시문 앞에 `/es-toolkit:migrate `를 붙인다. 플러그인 폴더에는 공식 `SKILL.md` 하나만 넣는다(바이트 단위로 같음).                                                                                                                                         |
| placebo  | 지시문 앞에 `/es-toolkit:migrate `를 붙인다. `SKILL.md` 본문, `description`, `argument-hint`를 비슷한 분량의 일반론으로 바꾼다. es-toolkit, strict, compat, 번들, 실행이나 확인 지시는 넣지 않는다. 원문은 `suites/es-toolkit/migrate/arms/placebo.md`다. |

모델은 Sonnet 5.5(`claude-sonnet-5-5`)와 Haiku 5.5(`claude-haiku-5-5`)다. 모든 실행은 같은 Claude Code 버전, 같은 도구 권한으로 한다. 실행 순서는 프로젝트·모델·조건·반복을 섞어 무작위로 정한다.

지시문은 플러그인 README의 사용 예처럼 쓴다. 판단 규칙(어느 진입점을 쓸지)이나 채점 기준은 알려 주지 않는다.

```text
Migrate this project from lodash to es-toolkit. Replace every use of lodash in the project and remove lodash from its dependencies. es-toolkit 1.53.2 is already installed in node_modules; add it to package.json yourself. The network is offline, so do not run package installs. Keep the existing behaviour. Do not ask questions; decide yourself.
```

## 4. 실행 환경

- `claude -p`를 사용자 설정, MCP, 다른 플러그인과 격리해 실행한다.
- 실행마다 fixture를 새 작업 폴더로 복사한다. 실행이 끝나면 base 커밋 대비 변경을 `changes.patch`로 저장하고 작업 폴더를 지운다. 채점은 나중에 이 패치를 새 fixture 사본에 적용해서 한다.
- 파일 편집과 셸 명령은 허용한다. 에이전트는 프로젝트의 테스트를 직접 돌려 볼 수 있다. 실제 개발자도 그렇게 하기 때문이다.
- 네트워크는 두 겹으로 막는다.
  - 자식 프로세스 환경에 닿지 않는 프록시와 `NODE_USE_ENV_PROXY=1`을 넣고, Anthropic API 호스트만 `NO_PROXY`로 뺀다.
  - 실행 기록에서 외부 접근 시도를 찾는다. 프록시를 따르지 않아 차단을 우회할 수 있는 시도만 오염으로 분류한다. 해당하는 것은 PowerShell `Invoke-WebRequest`·`Invoke-RestMethod`, `Net.WebClient`, `Start-BitsTransfer`, `node:http`·`net` 직접 사용, `WebSocket`, 프록시 변수 변경, WebFetch·WebSearch다. 프록시가 막는 시도(`fetch`, `curl`, 패키지 설치, URL을 담은 명령)는 정보를 얻지 못하므로 분석에 넣고 조건별 비율만 보고한다. URL 문자열만으로 오염 처리하면 문서 링크를 다루는 Skill 조건만 더 많이 빠지는 편향이 생긴다.
- 실행 상태는 정상 종료, 시간·턴 한도, 인프라 실패, 오염으로 나눈다. 인프라 실패만 다시 실행한다. 시간·턴 한도에 걸린 실행은 0점으로 넣는다. 오염 실행은 분석에서 빼고 조건별 개수를 보고한다.
- 에이전트가 정답 자료(이 저장소, 숨김 검사, fixture 메타데이터)에 접근했는지 실행 기록에서 검사해 보고한다.

## 5. 채점

실행 하나의 점수는 아래 항목 가운데 통과한 항목의 비율(0~1)이다.

### 5.1 전환 항목

| 항목            | 통과 조건                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| lodash 제거     | 소스, 테스트, 템플릿, 타입 정의에 `lodash`, `lodash/*`, `lodash-es`, `lodash.*` import·require·타입 참조가 없다.                |
| 의존성 정리     | `package.json`의 dependencies·devDependencies·peerDependencies에 lodash 계열과 `@types/lodash*`가 없다.                         |
| es-toolkit 선언 | 배포 코드를 담은 `package.json`의 dependencies에 es-toolkit이 있다.                                                             |
| 타입 검사·빌드  | 프로젝트의 타입 검사 또는 빌드 명령이 성공한다. swagger-typescript-api는 원래 커밋에서도 `tsc` 오류가 355개라 빌드 명령을 쓴다. |
| 기존 테스트     | 원래 커밋에서 통과하던 테스트가 모두 통과한다. 원래 커밋에서 실패하던 테스트(recharts의 로캘 표기 테스트 1개)는 제외한다.       |

lodash는 다른 패키지의 간접 의존성으로 `node_modules`에 남는다. 그래서 lodash import가 남아 있어도 테스트는 통과한다. 이 때문에 lodash 제거와 의존성 정리를 따로 검사한다.

### 5.2 숨김 검사

프로젝트의 lodash 호출 지점마다, 그 지점을 지나는 프로젝트 코드(export 함수, selector, 생성 결과)를 lodash와 대체 구현의 동작이 갈리는 입력으로 호출한다. 기대값은 원래 커밋(lodash)의 결과다. 검사 하나가 항목 하나다.

- 입력은 그 호출 지점에 실제로 들어올 수 있는 값으로 고르고, 근거를 주석에 적는다.
- 모든 검사는 원래 커밋에서 통과해야 한다.
- 사람이 머지한 전환 PR에 적용해 어느 검사가 실패하는지 기록한다. 예를 들어 recharts PR은 `max([])`(`undefined`)를 `Math.max(...[])`(`-Infinity`)로 바꿨고, swagger-typescript-api PR은 깊은 병합을 얕은 복사로, `flatten`을 `flattenDeep`으로 바꿨다. 기존 테스트는 이 변경을 잡지 못했다.
- 숨김 검사는 작업 폴더에 넣지 않고 채점할 때만 복사한다.

### 5.3 부차 지표

판정하지 않고 보고한다.

- 항목별 통과율과 조건별 차이
- 바뀐 파일 수와 줄 수
- 함수별로 쓴 진입점(strict, compat, 네이티브)
- 실행 비용(모델별 공식 단가), 시간, 턴 수
- 조작 확인: Skill 로드 여부, 설치된 es-toolkit을 확인했는지, es-toolkit 소스를 읽었는지, lodash와 직접 비교했는지

## 6. 판정 질문

프로젝트(2) × 모델(2)마다 두 가지를 판정한다. 모두 8개다.

| 기호 | 판정 문장                                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| H_a  | 평가 시스템은 [프로젝트] 전환에서 [모델]의 공식 Skill 실행 점수가 baseline 실행 점수와 비교해 높은지, 낮은지, ±15pp 안에서 같은지 판정한다. |
| H_b  | 평가 시스템은 [프로젝트] 전환에서 [모델]의 공식 Skill 실행 점수가 placebo 실행 점수와 비교해 높은지, 낮은지, ±15pp 안에서 같은지 판정한다.  |

결론은 프로젝트·모델마다 아래 표로만 쓴다.

| baseline 대비 | placebo 대비        | 결론                                                                                      |
| ------------- | ------------------- | ----------------------------------------------------------------------------------------- |
| 높음          | 높음                | 공식 Skill의 내용이 이 프로젝트 전환에서 이 모델의 점수를 높였다.                         |
| 높음          | 동등 또는 판정 불가 | 공식 Skill이 점수를 높였지만, 내용 때문인지 지시문을 넣는 행위 때문인지 가를 수 없다.     |
| 높음          | 낮음                | 공식 Skill이 점수를 높였지만 placebo가 더 높였다. 공식 Skill 내용의 효과라는 근거는 없다. |
| 동등          | 무엇이든            | 공식 Skill은 이 프로젝트 전환에서 이 모델의 점수를 15pp 넘게 바꾸지 않는다.               |
| 낮음          | 무엇이든            | 공식 Skill이 점수를 낮췄다.                                                               |
| 판정 불가     | 무엇이든            | 이 규모로는 판정할 수 없다. 95% 구간을 보고한다.                                          |

Δ = 15pp는 SkillsBench가 보고한 큐레이션 Skill의 통과율 향상(에이전트별 +14.1~+23.3pp) 가운데 가장 작은 값이다.

결론은 시험한 두 프로젝트와 두 모델에만 적용하고, 다른 프로젝트로 일반화하지 않는다.

## 7. 통계 분석

- **분석 단위는 실행이다.** 같은 프로젝트·모델에서 조건마다 K번 독립 실행한다.
- **차이 검정:** 두 조건의 실행 점수에 두 표본 순열 검정(평균 차이)을 쓴다.
- **동등 검정:** 처리 조건 표본을 ±15pp 이동한 두 단측 순열 검정(TOST)이다.
- **구간:** 순열 검정을 뒤집어 만든 95% 구간이다.
- **다중 비교:** 8개 차이 검정과 8개 동등 검정에 각각 Holm 보정을 적용하고, 전체 유의수준은 α = 0.05다.
- **판정 순서:** 차이가 유의하면 높음·낮음, 아니면 동등이 유의할 때 동등, 둘 다 아니면 판정 불가다.

### 7.1 반복 횟수 정하기

1. 스모크 실행(프로젝트·모델·조건마다 2회)으로 실행 시간, 턴 수, 점수의 분산을 측정한다. 스모크 실행은 본 실험 분석에 쓰지 않는다.
2. 시간·턴 한도는 스모크 실행의 최대 시간과 턴 수의 2배로 정한다.
3. 프로젝트·모델마다 점수 표준편차의 95% 상한으로 모의실험을 돌린다. 차이가 15pp일 때 "높음"을 판정할 확률과, 차이가 0일 때 "동등"을 판정할 확률이 Holm 8개 아래에서 모두 0.8 이상인 가장 작은 K를 고른다.
4. 그 K의 예상 실행 시간이 마감까지 남은 시간을 넘으면, K를 시간에 맞추고 그때의 검출력을 사전 등록에 적는다.

## 9.1 지난 설계(파일 단위)에서 바뀐 것

파일 하나짜리 합성 과제 22개로 파일럿을 했다. Skill 없는 Sonnet 5.5가 전환 정확성 96%, 차이 판단 97% 이상을 달성해 Skill이 높일 여지가 없었다. Skill이 실제로 쓰이는 상황(기존 프로젝트 전체 전환)과도 거리가 있었다. 그래서 실제 프로젝트 단위로 바꿨다. 이 파일럿에서 찾은 결함 두 가지를 이 설계에 반영했다.

- 범위 검사기와 문서의 입력 범위가 달랐다.
- 네트워크 오탐(입력 문자열 `XMLHttpRequest`, URL 문자열)이 있었다.

## 10. 한계

- 프로젝트는 두 개다. 결론은 프로젝트·모델별이고 일반화하지 않는다.
- 숨김 검사는 동작이 갈리는 지점을 사람이 골라 만든 것이다. 모든 동작 차이를 잡지는 못한다.
- 에이전트는 프로젝트 테스트를 볼 수 있다. 기존 테스트 항목은 에이전트가 직접 확인할 수 있는 기준이다.
- Skill 자동 호출은 측정하지 않는다. 슬래시 명령으로 호출을 강제한다.
- Skill이 내는 설명(기능 비교표, 문서 링크)의 품질은 채점하지 않는다.
- 실행 환경은 Windows 11이다. 로캘과 줄바꿈 설정은 fixture에서 고정했다.
