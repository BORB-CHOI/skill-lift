# `es-toolkit:migrate` Skill의 목적 달성 평가 설계

이 문서는 실행 전에 고정하는 설계다. 파일럿 결과로 채울 값(과제 수 N, 반복 횟수 K, 분산 추정치)은 정하는 규칙만 적고, 값은 사전 등록 파일에 넣는다.

## 1. 평가 대상과 목적

평가 대상은 toss/es-toolkit 저장소의 Claude Code 플러그인에 들어 있는 `migrate` Skill이다(`es-toolkit-plugin/skills/migrate/SKILL.md`, blob `3a83c14`).

| 출처                          | 내용                                                                                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 플러그인 README, Skills 표    | `migrate`는 lodash 코드를 es-toolkit으로 전환하도록 안내하고, strict와 compat API의 차이를 이해시킨다.                                                                 |
| 플러그인 README, How It Works | Skill은 프로젝트에 설치된 es-toolkit 버전에서 export와 타입 선언을 읽는다.                                                                                             |
| `SKILL.md` 판단표             | 양쪽에 있고 동작이 같으면 strict(번들이 더 작다), 동작이 다르면 차이를 설명하고 사용자가 고르게, compat에만 있으면 compat, 어디에도 없으면 lodash 유지나 최신 JS 문법. |

이 평가는 Skill의 목적을 두 가지로 정의한다.

- **목적 1. 전환 정확성:** 함수마다 판단표에 맞는 진입점으로 전환하고, 기존 동작을 유지한다.
- **목적 2. 차이 판단의 정확성:** 함수마다 strict 구현이 이 코드의 입력 범위에서 lodash와 같게 동작하는지 정확히 판단한다.

번들 크기, 실행 비용, 동작 보존만 본 점수는 부차 지표로 보고하고 판정하지 않는다.

## 2. 판정 질문

판정 주체는 재채점 스크립트의 판정 함수다. 모델은 Sonnet 5.5(`claude-sonnet-5-5`) 하나다.

| 번호 | 판정 문장                                                                                                                                |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| H1   | 공식 Skill을 넣은 실행의 목적 1 점수가 Skill 없이 한 실행(baseline)의 목적 1 점수와 비교해 높은지, 낮은지, ±15pp 안에서 같은지 판정한다. |
| H2   | 공식 Skill을 넣은 실행의 목적 2 점수가 baseline 실행의 목적 2 점수와 비교해 높은지, 낮은지, ±15pp 안에서 같은지 판정한다.                |
| H3   | 공식 Skill을 넣은 실행의 목적 1 점수가 placebo를 넣은 실행의 목적 1 점수와 비교해 높은지, 낮은지, ±15pp 안에서 같은지 판정한다.          |
| H4   | 공식 Skill을 넣은 실행의 목적 2 점수가 placebo를 넣은 실행의 목적 2 점수와 비교해 높은지, 낮은지, ±15pp 안에서 같은지 판정한다.          |

Δ = 15pp는 파일럿 전에 고정했다. 근거는 SkillsBench가 보고한 큐레이션 Skill의 통과율 향상(에이전트별 +14.1~+23.3pp) 가운데 가장 작은 값이다. 그래서 "동등"은 "공식 Skill의 효과가 일반적으로 보고된 좋은 Skill의 효과보다 작다"는 뜻이다.

### 2.1 결과 조합과 결론의 대응

결론은 아래 표로만 쓴다. 목적 1(H1, H3)과 목적 2(H2, H4)에 각각 적용한다.

| baseline 대비(H1·H2) | placebo 대비(H3·H4) | 결론                                                                                             |
| -------------------- | ------------------- | ------------------------------------------------------------------------------------------------ |
| 높음                 | 높음                | 공식 Skill의 내용이 목적 달성률을 높였다.                                                        |
| 높음                 | 동등 또는 판정 불가 | 공식 Skill이 목적 달성률을 높였지만, 내용 때문인지 지시문을 넣는 행위 때문인지 가를 수 없다.     |
| 높음                 | 낮음                | 공식 Skill이 목적 달성률을 높였지만 placebo가 더 높였다. 공식 Skill 내용의 효과라는 근거는 없다. |
| 동등                 | 무엇이든            | 공식 Skill은 목적 달성률을 15pp 넘게 바꾸지 않는다.                                              |
| 낮음                 | 무엇이든            | 공식 Skill이 목적 달성률을 낮췄다.                                                               |
| 판정 불가            | 무엇이든            | 이 규모로는 판정할 수 없다. 95% 구간을 보고한다.                                                 |

## 3. 실험 조건

| 조건     | 에이전트에게 주는 것                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| baseline | 과제 지시문만 준다. 플러그인을 넣지 않는다.                                                                                                        |
| skill    | 지시문 앞에 `/es-toolkit:migrate `를 붙인다. 플러그인 폴더에는 공식 `migrate` Skill 하나만 넣는다.                                                 |
| placebo  | 지시문 앞에 `/es-toolkit:migrate `를 붙인다. 플러그인 폴더에는 `migrate` Skill 하나만 넣되 본문과 frontmatter의 `description`을 일반론으로 바꾼다. |

placebo 원문은 사전 등록에 넣는다. 아래 규칙으로 쓴다.

- 이름은 `migrate`로 같다. `description`은 비슷한 길이의 일반 문장으로 바꾸고 strict, compat, 번들을 언급하지 않는다.
- 본문은 공식 Skill과 비슷한 분량의 일반 코드 작성 원칙이다. es-toolkit의 함수, 진입점, 동작 차이를 다루지 않는다.
- 설치된 패키지를 확인하라거나 실행해서 검증하라는 지시도 넣지 않는다. 이런 지시는 공식 Skill의 핵심 동작이라서, placebo에 넣으면 H3·H4가 그 동작의 효과를 분리하지 못한다.

세 조건은 같은 과제, 같은 작업 폴더, 같은 모델, 같은 도구 권한, 같은 Claude Code 버전으로 실행한다. 실행 순서는 조건과 과제를 섞어 무작위로 정한다.

## 4. 과제

### 4.1 과제 하나의 구성

과제 하나는 lodash 함수 3개를 쓰는 TypeScript 모듈 하나다. 모듈은 함수 3개를 export하고, 각 export 함수는 lodash 함수 하나를 감싼다. 이 export 함수 하나가 채점 단위인 **항목**이다. **lodash 함수 하나는 과제 하나에만 쓴다.** 과제끼리 독립이어야 과제 단위 검정이 성립해서다.

각 export 함수에는 TypeScript 타입과 한 줄짜리 JSDoc으로 입력 범위를 적는다. JSDoc은 타입이 허용하는 값의 범위만 쓰고, 동작이 갈리는 특정 값을 따로 짚지 않는다. 숨김 입력은 이 범위 안에서만 생성하고, 범위 검사기는 과제마다 코드로 둔다.

타이머에 의존하는 함수(`debounce`, `throttle` 등)는 반환값 비교로 동작을 판정할 수 없어서 쓰지 않는다.

### 4.2 항목의 유형과 정답

정답은 설치된 es-toolkit v1.53.2와 lodash 4.18.1을 직접 실행해 계산한다. 비교는 export 함수 단위다. 원본 모듈과, 그 lodash 호출만 strict(또는 compat) 함수로 바꾼 모듈에 같은 숨김 입력 3,000개를 넣는다.

"strict가 같게 동작한다"는 같은 인자로 호출했을 때를 말한다. 유형별 정답은 아래와 같다.

| 유형 | 조건(입력 범위 안에서, 같은 인자로 호출) | 목적 1에서 인정하는 진입점                       | 목적 2 정답                |
| ---- | ---------------------------------------- | ------------------------------------------------ | -------------------------- |
| S    | strict가 lodash와 같게 동작한다.         | strict만                                         | `strictSameAsLodash: true` |
| D    | strict가 lodash와 다르고, compat은 같다. | compat, 또는 호출 방식을 바꿔 동작을 지킨 strict | `false`와 범위 안의 반례   |
| C    | strict에 함수가 없고 compat에만 있다.    | compat                                           | `false`, 반례 없음         |

- **strict 진입점:** `es-toolkit`, 또는 `es-toolkit/compat`과 `es-toolkit/fp`를 제외한 `es-toolkit/...` 하위 경로.
- **compat 진입점:** `es-toolkit/compat`과 그 하위 경로.

D 항목에서 호출 방식을 바꾼 strict를 인정하는 근거는 두 가지다. `groupBy(rows, 'age')`를 `groupBy(rows, (r) => r.age)`로 바꾸는 식의 전환은 Skill 본문의 전후 코드 예시가 안내하는 방식이다. 또 동작 보존은 숨김 입력 비교로 따로 확인한다.

strict도 compat도 lodash와 같지 않은 함수(분류상 X)는 과제에 넣지 않는다. Skill 판단표는 "compat에 있지만 동작이 다르다"는 경우를 다루지 않아서, 이런 항목은 Skill의 목적 밖이다.

목적 2에서 "항상 `false`"로 답하는 전략을 막는 장치는 두 가지다. 첫째, S 항목은 전체 항목의 1/3 이상이 되게 넣는다. 둘째, D 항목은 범위 안의 유효한 반례를 내야 점수를 준다. 목적 2 점수는 유형별로도 나눠 보고한다.

### 4.3 후보 선정 절차

1. 후보 함수를 모은다. es-toolkit v1.49.0~v1.53.2 변경 이력에서 strict 또는 compat의 동작 변경이 기록된 함수와, 설치본에서 strict 없이 compat에만 있는 함수가 대상이다.
2. 함수마다 실무 코드에서 흔한 사용 방식 하나를 정하고, 그 방식의 입력 생성기와 범위 검사기를 만든다.
3. 4.2의 방법으로 유형을 정한다.
4. 항목 3개씩 묶어 후보 과제를 만든다. 함수는 재사용하지 않는다.
5. 과제마다 기준 해답을 만든다. S 항목은 strict, D·C 항목은 compat을 쓴다.
6. 채점기 관문(10절)을 비공개 숨김 입력으로 돌린다. 기준 해답이 동작 보존에 실패한 항목은 compat도 lodash와 다른 것(X)으로 보고 `exclusions.json`에 사유와 함께 적은 뒤, 과제를 다시 만든다.

분류용 입력은 20,000개이고 시드는 공개한다. 반례가 JSON으로 표현되지 않는 값(NaN, -0, undefined, 배열의 빈 칸)에 몰려 있어서, 보고서의 반례는 JavaScript 리터럴 문자열로 받는다. 채점기는 이 문자열을 실행하지 않고, TypeScript 파서로 허용된 구문만 해석해 값을 만든다.

### 4.4 파일럿으로 과제를 거르는 규칙

파일럿은 후보 과제마다 baseline 조건만 4회 실행한다. 공식 Skill과 placebo는 실행하지 않는다.

- **거르기(1~2회차):** 목적별로 따로 거른다. 1~2회차의 항목 점수 6개 가운데 2개 이상 틀린 과제(평균 ≤ 0.67)만 그 목적의 가설(H1·H3 또는 H2·H4)에 쓴다.
- **추정(3~4회차):** 남은 과제의 3~4회차로 baseline 평균과 분산을 추정해 8.1의 검출력 계산에 쓴다. 거르기에 쓴 실행과 추정에 쓴 실행을 나눠서, 낮은 점수를 골라낸 데서 오는 과소 추정을 막는다.
- **결함 점검:** 남은 과제의 baseline 오답을 모두 보고 "모델 판단 오류"와 "지시문이나 범위의 모호함"으로 나눈다. 모호함 때문에 틀린 과제는 고치지 않고 버린다.

본 실행에서는 세 조건을 모두 새로 실행한다. 파일럿 실행은 본 실행 분석에 쓰지 않는다.

### 4.5 한도 설정용 스모크 실행

공식 Skill은 기능 비교표 같은 긴 산출물을 요구해서 실행이 길어질 수 있다. 그래서 4.4에서 버린 과제 3개로 skill과 placebo 조건을 각 2회 실행한다. 여기서 턴 수, 시간, 보고서 작성률을 측정해 시간·턴 한도를 정한다. 이 실행은 과제 선택에 쓰지 않는다.

## 5. 에이전트 지시문

실행 하나는 두 턴이다. 첫 턴에서 전환하고, 같은 세션을 이어 받아(`--resume`) 두 번째 턴에서 보고서를 쓴다. 목적 1은 첫 턴이 끝난 시점의 `out/module.ts`로 채점한다. 보고서 요구가 전환 행동을 바꾸지 않게 하려고 턴을 나눈다.

첫 턴(skill과 placebo는 앞에 `/es-toolkit:migrate `를 붙인다):

```text
Convert the lodash imports in src/module.ts to es-toolkit and write the result to out/module.ts. We are moving to es-toolkit to reduce bundle size. For each lodash function: use the main es-toolkit entry if it keeps the existing behaviour for the inputs described in the JSDoc; otherwise use es-toolkit/compat if that keeps the behaviour; if neither keeps it, keep the lodash import. Keep the exported signatures. Do not ask questions; decide yourself.
```

두 번째 턴(모든 조건 같음):

```text
Write out/migration-report.json in this shape:
{ "functions": [ { "lodash": "<lodash function name>", "strictSameAsLodash": <true|false>, "counterexample": <string or null> } ] }
"counterexample" is a string holding a JavaScript array literal: the argument list for the exported function, e.g. "[[1, NaN, -0], undefined]". Allowed syntax: number, string, boolean, null, undefined, NaN, Infinity, unary minus, array literals (holes allowed), plain object literals, new Set([...]), new Map([...]), new Date(<number>), Object.create(null).
"strictSameAsLodash" is true if the function of the same name from the main "es-toolkit" entry, called with the same arguments as the original lodash call, returns the same result as lodash for every input in the JSDoc range of the exported function that uses it. If it is false and that function exists in the main entry, give one argument list, within the JSDoc range, for which the results differ.
```

첫 턴의 판단 규칙은 판단표를 사용자 결정으로 옮긴 것이다. 이 규칙을 세 조건에 똑같이 알려 주므로, 공식 Skill이 더할 수 있는 것은 "설치된 버전에서 어느 함수의 동작이 같은지 아는 지식"뿐이다. 이는 README가 밝힌 Skill의 목적이다.

## 6. 채점

### 6.1 목적 1

항목마다 아래가 모두 맞으면 1점, 아니면 0점이다.

1. 첫 턴의 `out/module.ts`가 `tsc` 타입 검사를 통과한다.
2. 숨김 입력 3,000개에서 원본과 결과가 같다. 같음의 정의는 `src/graders/equal.ts`를 따르고 사전 등록에 고정한다. 예외는 예외끼리 같은 것으로 본다. 인자 변형(mutation) 결과도 비교한다.
3. 그 lodash 함수를 대체한 import가 4.2 표의 인정 진입점과 맞는다. lodash import를 남기거나, 직접 구현으로 바꾸거나, lodash 소스를 복사하면 틀린다.

### 6.2 목적 2

항목마다 보고서에서 그 lodash 함수의 줄을 찾아 채점한다. 아래가 모두 맞으면 1점이고, 하나라도 틀리거나 줄이 없거나 보고서가 없으면 0점이다.

1. `strictSameAsLodash`가 4.2의 정답과 맞는다.
2. `false`이고 strict에 그 함수가 있으면, `counterexample`이 범위 검사기를 통과하고, 원본 모듈과 strict로 바꾼 모듈에서 결과가 달라야 한다.

S 항목에서 에이전트가 범위 안의 유효한 반례를 내면 정답으로 인정하고, 그 항목을 D로 재분류한다. 재분류는 실행이 끝난 뒤 모든 조건에 똑같이 적용하고 기록을 남긴다. 생성 입력이 놓친 차이를 에이전트가 찾았을 때 그 에이전트를 오답 처리하지 않으려는 규칙이다.

### 6.3 부차 지표

판정하지 않고 수치만 보고한다.

- 동작 보존만 본 점수(6.1의 1·2)
- 번들 크기: 목적 1을 통과한 제출물의 esbuild min+gzip 바이트, 기준 해답 대비 비율
- 실행 비용: Sonnet 5.5 공식 단가로 계산한 달러(1M 토큰당 입력 $2, 출력 $10, 캐시 읽기 $0.10, 캐시 쓰기는 입력의 1.25배)
- 실행 시간, 턴 수

### 6.4 조작 확인

"Skill이 불리지 않았다"거나 "무시됐다"는 반박을 막으려고 조건별로 아래를 집계한다.

- init 메시지에 로드된 Skill 이름
- Skill 본문의 확인 명령(`require('es-toolkit/package.json')` 등)을 실행한 비율
- es-toolkit의 `dist` 타입 선언이나 소스를 읽은 비율
- lodash와 es-toolkit을 직접 실행해 비교한 비율

## 7. 실행 환경

- `claude -p`를 사용자 설정, MCP, 다른 플러그인과 격리해 실행한다. Claude Code 버전은 사전 등록에 고정한다.
- 작업 폴더에는 lodash 4.18.1, `@types/lodash`, es-toolkit v1.53.2, TypeScript를 설치한다.
- 파일 편집과 셸 명령은 허용한다.
- 네트워크는 두 겹으로 막는다.
  - 자식 프로세스 환경에 닿지 않는 프록시(`HTTP_PROXY`, `HTTPS_PROXY`)와 `NODE_USE_ENV_PROXY=1`을 넣고, Anthropic API 호스트만 `NO_PROXY`로 뺀다.
  - 실행 기록에서 외부 접근 시도(`fetch`, `http`, `Invoke-WebRequest`, URL 문자열을 쓰는 명령)를 찾아 그 실행을 "오염"으로 분류한다.
- 실행 상태는 정상 종료, 시간·턴 한도, 인프라 실패, 오염으로 나눈다.
  - 인프라 실패(API 오류, 연결 실패)만 다시 실행한다.
  - 시간·턴 한도에 걸린 실행은 두 목적 모두 0점으로 넣는다.
  - 오염 실행은 분석에서 빼고 조건별 개수를 보고한다. 한 조건이라도 5%를 넘으면 결론에 한계로 적는다.
- 차단이 실제로 작동하는지는 본 실행 전에 프로브로 확인한다. API 호출은 되고 `fetch`는 실패해야 한다.

## 8. 통계 분석

- **분석 단위는 과제다.** 과제마다 조건별로 "실행별 항목 평균"의 평균을 내고, 처리 조건에서 대조 조건을 뺀 차이를 과제 하나의 값으로 쓴다.
- **차이 검정:** 과제별 차이에 양측 부호 뒤집기 정확 검정을 쓴다.
- **동등 검정:** 차이가 -15pp보다 크다는 검정과 +15pp보다 작다는 검정을 각각 부호 뒤집기로 하고, 둘 다 유의하면 동등이다(TOST).
- **구간:** 부호 뒤집기 검정을 뒤집어 만든 95% 구간을 주 구간으로 보고한다. BCa 구간은 참고로 함께 낸다.
- **다중 비교:** H1~H4의 차이 검정에 Holm 보정을 적용하고, 전체 유의수준은 α = 0.05다. 동등 검정도 같은 방식으로 보정한다.
- **판정:** 2절의 세 판정(높음·낮음, 동등, 판정 불가)과 2.1의 대응표로만 결론을 쓴다.

### 8.1 검출력과 규모를 정하는 절차

1. 4.4 추정 실행(3~4회차)으로 과제 수준 무작위 효과를 넣은 로짓 척도 모형을 맞춘다. 과제 간 분산은 95% 구간 상한을 쓴다.
2. 이 모형에서 처리 조건의 평균 점수를 Δ = 15pp 올린 데이터를 1,000번 만든다. 효과가 과제마다 다른 경우도 함께 만든다. 8절 절차(Holm 4개 포함)가 "높음"을 판정하는 비율을 센다.
3. 차이가 0인 데이터에서 "동등"을 판정하는 비율도 같은 방식으로 센다.
4. 남은 과제 수 N 안에서 반복 횟수 K를 바꿔 가며, 두 비율이 네 가설 모두에서 0.8 이상인 가장 작은 K를 고른다. 기준은 효과가 모든 과제에 고르게 나는 경우로 판단한다. 효과가 과제마다 다른 경우(효과의 표준편차를 평균과 같게 둔다)의 검출력은 함께 보고하되 기준에 넣지 않는다.
5. 어떤 K로도 0.8에 닿지 않으면 후보 과제를 추가해 파일럿을 한 번 더 한다. 두 번째에도 닿지 않으면 본 실행을 하지 않고 그 결과를 보고한다.

### 8.2 판정 절차 자체의 검증

본 실행 뒤에 보고한다.

- 반분 재표집: baseline 실행을 둘로 나눠 차이가 없는 데이터를 만들고, 판정 절차가 "높음·낮음"을 내는 비율을 측정한다. 분할끼리 독립이 아니므로 오판정률의 추정치가 아니라 구현 확인용이다.
- 검출력 곡선: baseline 데이터에 차이를 인위로 넣어 검출률을 측정한다.

## 11. 한계

- 모델은 Sonnet 5.5 하나다.
- 과제는 합성 모듈이다. 실제 코드베이스의 전환 작업보다 작고 단순하다.
- 항목은 동작 변경이 기록된 함수와 compat 전용 함수에서 골랐다. 파일럿에서 baseline이 대부분 맞힌 과제를 버렸다. 그래서 결과는 "Skill 없이는 틀릴 수 있는 전환에서의 효과"이고, 모든 전환 작업의 평균 효과가 아니다.
- 판단 규칙을 지시문으로 알려 줬다. 실제 사용자가 이 규칙을 말하지 않는 경우의 효과는 측정하지 않는다.
- Skill이 내는 설명(기능 비교표, 문서 링크, 전후 코드)의 품질은 채점하지 않는다. 목적 2는 strict와 lodash의 동작이 같은지에 대한 판단만 채점한다.
- Skill 자동 호출은 측정하지 않는다. 슬래시 명령으로 호출을 강제한다.
