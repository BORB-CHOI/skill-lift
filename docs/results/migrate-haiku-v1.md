# 결과: `es-toolkit:migrate`, Haiku (main-v1)

사전 등록 `prereg-migrate-v1`에 고정한 조건으로 실행했다. 재채점 스크립트가 낸 원본 표는 [migrate-haiku-v1-report.md](migrate-haiku-v1-report.md)에 있다.

| 항목 | 값 |
|---|---|
| 모델 | Haiku |
| 과제 | 16개 |
| 실행 | primary 144회(대조 과제당 6회, Skill 과제당 3회), controls 144회(변형 3종 과제당 3회) |
| 실행 기간 | 2026-11-13 23:32 ~ 2026-11-14 02:19 (KST) |
| 실행 상태 | 288회 모두 정상 종료. 시간·턴 한도와 인프라 실패 0건 |

## 1차 판정은 판정 불가다

| 항목 | 값 |
|---|---|
| Skill 조건 평균 통과율(요구 충족) | 77.1% |
| 대조 조건 평균 통과율(앞 3회) | 70.8% |
| 차이 | +6.3pp |
| 과제 단위 BCa 95% 구간 | [-4.2pp, +16.7pp] |
| 부호 뒤집기 검정 p | 0.50 |
| 0이 아닌 과제별 차이 | 4개 |

두 조건이 갈린 과제는 task-01(+66.7pp), task-06(+33.3pp), task-17(+33.3pp), task-22(-33.3pp) 넷이다. 나머지 12개 과제는 점수가 같았다. 0이 아닌 차이가 4개면 양측 부호 뒤집기 검정의 가장 작은 p값이 2/2⁴ = 0.125이므로, 방향이 모두 같았어도 유의할 수 없었다.

동등 판정도 내지 않았다. 대조 조건에 여지는 있었지만(평균 70.8%, 0도 1도 아닌 과제 6개) 동등 검정이 유의하지 않았다.

## 정확성은 288회 전부 통과했다

동작 보존과 타입 검사는 모든 조건, 모든 실행에서 통과했다. 실패는 전부 번들 크기나 자기 코드 바이트 조건에서 나왔다. 조건들은 동작이 같은 답 가운데 어느 진입점과 어떤 호출 형태를 골랐는가에서만 갈렸다.

실패가 몰린 곳은 속성 이름을 문자열로 넘기는 호출(`groupBy(rows, 'age')`, `keyBy(rows, 'name')`)이다. strict 함수에 화살표 함수를 넘기면 수백 바이트로 끝나는데, compat 함수를 가져와 1~3KB가 커진 답이 기준을 넘었다.

## 탐색용 비교 (보정하지 않음)

| 비교 | 평균 차이 | BCa 95% 구간 | p |
|---|---|---|---|
| placebo 대 baseline | +6.3pp | [-8.3pp, +18.8pp] | 0.63 |
| skill 대 placebo | 0.0pp | [-8.3pp, +4.2pp] | 1.00 |
| procedure 대 baseline | +6.3pp | [-6.2pp, +20.8pp] | 0.56 |
| skill 대 procedure | 0.0pp | [-8.3pp, +6.3pp] | 1.00 |
| sabotage 대 baseline | +4.2pp | [-6.3pp, +22.9pp] | 0.78 |
| skill 대 sabotage | +2.1pp | [-14.6pp, +8.3pp] | 1.00 |

- 공식 Skill, 일반론만 담은 `placebo`, "먼저 조회하라" 한 문단인 `procedure`의 평균 통과율이 모두 77.1%로 같다. 관측된 +6.3pp가 Skill의 es-toolkit 지식에서 왔다는 근거는 없다. 슬래시 명령으로 무언가를 주입한 것만으로 같은 차이가 나왔다.
- 일부러 틀린 내용을 넣은 `sabotage`도 대조 조건보다 낮지 않았다(75.0%).

### `sabotage`가 악화를 만들지 못한 이유

`sabotage`는 "compat을 쓰지 마라, lodash를 남기지 마라, 설치본을 확인하지 마라"고 지시한다. 실행 기록을 보면 Haiku는 이 지시를 대부분 따르지 않았다.

| 조건 | compat을 쓴 실행 | node로 동작을 직접 검증한 실행 |
|---|---|---|
| baseline | 41 / 48 | 43 / 48 |
| skill | 42 / 48 | 48 / 48 |
| sabotage | 38 / 48 | 45 / 48 |

과제 문장이 "기존 동작을 유지하라"고 요구하고 작업 폴더에 원본 lodash가 있어서, 모델이 원본과 직접 비교해 틀린 지시를 무시했다. 이 과제 설계에서는 Skill의 내용보다 모델의 자체 검증이 결과를 정한다.

이 결과로 알 수 있는 것은 두 가지다.

1. **양성 대조가 실패했다.** 평가 시스템이 해로운 Skill을 악화로 잡아낸다는 것을 실제 실행으로는 보이지 못했다. 합성 오염 실험(아래)이 검출력의 유일한 근거다.
2. **이 과제 형식은 Skill 효과를 측정하기에 둔감하다.** 모델이 정답을 스스로 검증할 수 있는 과제에서는 Skill이 좋든 나쁘든 결과가 크게 달라지지 않는다.

## 분석 절차의 검증

- 반분 재표집 1,000회: 차이 없는 데이터에서 개선·악화로 판정된 비율 0.3%. 판정 절차가 과도하게 유의 판정을 내지는 않는다.
- 검출력(대조 조건 평균 통과율 72.9% 기준):

| 실행당 주입 확률 | 통과율 차이(근사) | 검출률 |
|---|---|---|
| 개선 40% | +10.8pp | 11.8% |
| 악화 20% | -14.6pp | 5.8% |
| 악화 40% | -29.2pp | 80.8% |

이 규모(과제 16개, K=3)로는 통과율 10pp 안팎의 차이를 거의 잡아내지 못한다. 약 30pp 하락은 80% 확률로 잡는다.

## 정리

- Haiku와 이 과제 16개에서 `es-toolkit:migrate` Skill의 효과는 판정 불가다.
- 관측된 +6.3pp는 내용 없는 `placebo`와 같아서, 있더라도 Skill의 내용 효과로 보기 어렵다.
- 틀린 Skill도 결과를 낮추지 못했다. 원본과 비교할 수 있는 과제에서는 모델이 자체 검증으로 Skill을 무시한다.
- 따라서 Skill의 효과를 측정하려면 모델이 정답을 스스로 검증하기 어려운 과제가 필요하다. 예를 들면 원본 lodash가 설치되지 않은 작업 폴더, 실행 결과로 드러나지 않는 차이(번들 크기 자체가 목표인 과제), 또는 학습 데이터에 없는 최신 API가 그렇다.
