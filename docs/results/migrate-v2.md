## 1차 판정은 두 모델 모두 판정 불가다

| 항목 | Haiku | Sonnet |
|---|---|---|
| Skill 평균 통과율(요구 충족) | 68.8% | 95.8% |
| 대조 평균 통과율(앞 3회) | 75.0% | 85.4% |
| 차이 | -6.2pp | +10.4pp |
| 과제 단위 BCa 95% 구간 | [-25.0pp, +6.3pp] | [-2.1pp, +29.2pp] |
| 부호 뒤집기 검정 p | 0.59 | 0.31 |
| 0이 아닌 과제별 차이 | 7개 | 6개 |
| 판정 사유 | 차이 검정도 동등 검정도 유의하지 않음 | 대조 조건이 천장에 가까움 |

- **Haiku:** Skill 쪽이 6.2pp 낮다. 갈린 과제 7개 가운데 Skill이 높은 과제가 3개, 낮은 과제가 4개다. 방향이 섞여 있어 p = 0.59다.
- **Sonnet:** Skill 쪽이 10.4pp 높다. 갈린 과제 6개 가운데 4개는 Skill이 높고 2개는 낮다. 사전 등록한 판정 규칙은 대조 조건 점수가 0도 1도 아닌 과제가 7개 이상이어야 차이를 판정한다. 0이 아닌 차이가 6개 이하면 가장 작은 p가 2/2⁶ = 0.031이라 α = 0.025 아래로 내려갈 수 없어서다. Sonnet 대조 조건에서 그런 과제는 4개(06·08·14·22)뿐이었다.
- 같은 Skill이 두 모델에서 반대 방향의 차이를 냈다. 두 차이 모두 우연 변동과 구분되지 않는다.

정확성(동작 보존과 타입 검사)은 Haiku에서 Skill 95.8%, 대조 95.8%로 같았다. Sonnet은 Skill 95.8%, 대조 100%이고 역시 판정 불가다. v1과 마찬가지로 1차 지표의 실패는 대부분 번들 크기나 자기 코드 조건에서 나왔다.

### Haiku에서 공식 Skill이 실패한 과제

Haiku Skill 조건은 과제 5개(06·08·14·16·22)에서 3회 모두 요구 충족에 실패했다. 이 과제들의 제출물은 strict 버전으로 충분한 함수(`kebabCase`, `words`, `toNumber`)까지 `es-toolkit/compat`에서 가져와 번들이 기준을 넘었다. 예를 들어 task-16에서 Skill 제출물은 2,164B, 대조 제출물은 818B다.

다만 실행 전체로 보면 차이가 작다. 제출물 하나가 compat에서 가져온 함수 개수의 평균은 Skill 1.35개, 대조 1.25개다. Skill 본문은 compat을 거치는 점진 전환을 "레거시에 권장"으로 소개하고 위험도를 compat은 "Low", strict는 "Higher"로 적는다. 이 문장이 compat 선택을 늘렸을 수 있지만, 이 데이터로는 확인할 수 없다.

## lodash를 빼도 모델은 스스로 검증했다

실행 기록에서 arm별 행동을 셌다. baseline은 앞 3회, 나머지는 3회 전부다. 집계 기준은 다음과 같다.

- compat 사용: 제출물이 `es-toolkit/compat`을 가져옴
- node 실행: Bash로 `node`나 `tsx`를 실행함
- 설치본 조회: 도구 입력에 `node_modules/es-toolkit` 경로가 들어 있음
- lodash 못 찾음: 도구 결과에 lodash 모듈을 찾지 못했다는 오류가 있음

| 모델 | arm | compat 사용 | node 실행 | 설치본 조회 | lodash 못 찾음 |
|---|---|---|---|---|---|
| Haiku v1 | baseline | 41/48 | 46/48 | 48/48 | 1/48 |
| Haiku v1 | sabotage | 38/48 | 48/48 | 48/48 | 4/48 |
| Haiku v2 | baseline | 41/48 | 46/48 | 48/48 | 43/48 |
| Haiku v2 | skill | 42/48 | 48/48 | 48/48 | 42/48 |
| Haiku v2 | sabotage | 39/48 | 48/48 | 48/48 | 38/48 |
| Sonnet v2 | baseline | 39/48 | 10/48 | 47/48 | 38/48 |
| Sonnet v2 | skill | 37/48 | 44/48 | 23/48 | 48/48 |
| Sonnet v2 | sabotage | 35/48 | 31/48 | 48/48 | 44/48 |

v1 문서의 같은 표와 node 실행 수가 조금 다르다(baseline 43 → 46). 이 표는 v1과 v2를 같은 판별 규칙으로 다시 센 값이다.

- **lodash 제거는 의도대로 작동했다.** v2에서는 대부분의 실행이 원본 lodash를 불러오려다 실패했다. v1에서는 이 오류가 거의 없었다.
- **그래도 `sabotage`의 "compat을 쓰지 마라"는 지켜지지 않았다.** Haiku 39/48, Sonnet 35/48이 compat을 썼다.
- **모델은 원본 대신 설치된 es-toolkit 소스를 읽었다.** 거의 모든 실행이 `node_modules/es-toolkit`을 열었다. compat 구현은 lodash 동작을 재현하려고 만든 코드라서, 원본이 없어도 그 소스를 읽으면 lodash와 같은 동작인지 판단할 수 있다.

따라서 v2도 양성 대조에 실패했다. 해로운 Skill을 실제 실행에서 악화로 잡아내지 못했다.

## 정리

- 두 모델 모두 `es-toolkit:migrate` Skill의 효과는 판정 불가다. 관측 방향은 Haiku -6.2pp, Sonnet +10.4pp로 서로 반대다.
- 두 모델 모두 내용 없는 `placebo`와 틀린 `sabotage`가 공식 Skill 이상이었다. Skill 내용의 효과라는 근거는 없다.
- 원본 lodash를 빼도 모델은 설치된 es-toolkit 소스를 읽어 스스로 검증했다. 이 과제 형식에서는 작업 폴더를 바꾸는 것만으로 자체 검증을 막을 수 없다.
- 이 평가 시스템은 차이가 없는 데이터에서 잘못된 유의 판정을 내지 않았고, 약 30pp 악화는 80% 안팎으로 잡는다. 판정 불가가 나온 이유는 판정 절차가 아니라 과제 집합에 있다. 대조 조건이 천장에 가깝고, 모델이 정답을 스스로 확인할 수 있다.
