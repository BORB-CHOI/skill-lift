# 평가 방법

이 문서는 `migrate` Skill 평가의 설계와 그 근거를 설명한다. 실행 전에 고정한 값은 [사전 등록 파일](../suites/es-toolkit/migrate/preregistration.json)에 있다.

## 1. 무엇을 주장하는가

> 고정한 과제 집합에서 `/es-toolkit:migrate`로 Skill을 강제 호출한 에이전트의 결과가 플러그인 없는 에이전트보다 과제에 명시된 요구를 더 잘 충족하는가.

판정은 개선, 악화, 동등, 판정 불가 중 하나다. 다음은 주장하지 않는다.

- 과제 집합, 모델, 버전 밖으로의 일반화. 과제는 무작위 표본이 아니다.
- 플러그인을 설치만 해 두고 자연어로 요청했을 때의 효과. Skill이 자동으로 호출되는 비율에 좌우되므로 별도의 추정 대상이다.
- Skill이 쓴 설명문(비교표, 차이 설명, 문서 링크)의 품질. 코드로 판정할 수 없다.

## 2. 비교 조건

| 조건        | 내용                                                       | 역할                                    |
| ----------- | ---------------------------------------------------------- | --------------------------------------- |
| `baseline`  | 플러그인 없음                                              | 대조                                    |
| `skill`     | 공식 `migrate` Skill, 프롬프트 앞에 `/es-toolkit:migrate ` | 처리                                    |
| `placebo`   | 이름·설정은 같고 본문은 라이브러리 교체 일반론             | 슬래시 명령 형식과 컨텍스트 증가의 효과 |
| `procedure` | "설치된 패키지를 먼저 조회하라"는 한 문단                  | 일반 검증 절차의 효과                   |
| `sabotage`  | 일부러 틀린 사실을 적고 검증 단계를 지운 본문              | 해로운 Skill을 악화로 잡아내는지        |

과제 문장은 모든 조건에서 글자 단위로 같다. 차이는 로드한 플러그인 폴더와 접두 하나뿐이다. 변형 조건은 공식 Skill의 frontmatter를 그대로 두고 본문만 바꾼다.

실행 환경은 모든 조건에서 같다.

- 사용자 설정·훅·MCP·CLAUDE.md를 실행 옵션으로 차단한다(`--setting-sources ""`, `--strict-mcp-config`). 차단 여부는 이어 쓰기 프로브로 확인했다. 격리하지 않은 실행은 전역 지침 문장을 맞혔고 격리한 실행은 맞히지 못했다.
- Bash는 두 조건 모두 전부 허용하고 네트워크 명령(`curl`, `wget`, `npm install` 등)은 거부한다. 공식 Skill이 frontmatter의 `allowed-tools`로 Bash 전체를 승인받기 때문에, 대조 조건만 제한하면 차이가 Skill 내용이 아니라 권한에서 나온다. 시험 실행에서 대조 조건만 명령이 거부돼 턴 수가 2~3배로 늘어난 것을 확인했다.
- 과제 의존성은 미리 설치해 실행마다 복사한다.

## 3. 과제

과제 하나는 lodash 함수 세 개를 쓰는 TypeScript 파일이다. 에이전트는 이 파일을 es-toolkit으로 옮겨 `out/`에 쓴다.

### 함수 목록과 조합 규칙

| 묶음                                         | 함수                                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| A: strict가 lodash와 같게 동작할 것으로 예상 | `merge`, `groupBy`(함수 인자), `pick`, `mapValues`, `camelCase`, `words`, `keyBy`(함수 인자), `kebabCase` |
| C: strict가 다르게 동작할 것으로 예상        | `startCase`, `groupBy`·`sumBy`·`keyBy`(속성 이름 인자)                                                    |
| B·D: compat에만 있거나 es-toolkit에 없음     | `truncate`, `isEmpty`, `toNumber`, `fromPairs`, `sortedUniq`                                              |

i번째 과제는 세 목록의 i번째 함수를 묶는다. 같은 lodash 함수가 겹치는 조합은 건너뛴다. 작성자가 과제를 하나씩 고르지 않으므로 Skill에 유리한 과제만 골랐다는 반박을 줄인다. A·C 구분은 예상일 뿐이고 정답은 아래의 기준 해답 계산이 정한다.

### 입력 범위는 생성기 코드로 정의한다

과제 문장의 입력 범위 설명과 채점 입력이 같은 생성기([gen.mjs](../suites/es-toolkit/migrate/lib/gen.mjs))에서 나온다. 함수마다 공개 예시 2건과, 같은 범위에서 뽑은 비공개 입력 3,000건으로 채점한다. 비공개 입력은 예시에만 맞춘 하드코딩을 잡는다.

범위를 글로만 적고 몇 건으로만 검사하던 시험 단계에서는, 범위 안에 es-toolkit이 lodash와 다르게 동작하는 입력이 있었는데 검사 입력에는 없어서 기준 해답이 틀렸다. 에이전트는 수십만 건을 무작위로 비교해 그 차이를 찾았다.

### 과제 채택 조건

과제마다 아래를 모두 충족해야 채택한다. 19개를 만들어 16개를 채택했다.

1. 동작과 타입이 보존되는 후보 조합이 있다.
2. **크기 분리 조건**: 기준 해답과, 그보다 큰 후보 중 가장 작은 것의 크기 차이가 허용 오차의 2배 이상이다. 차이가 작으면 잘못 고른 답이 허용 오차 안에 들어와 통과한다.
3. 치환 스크립트 3종(전부 compat, 전부 strict, 그대로 둠) 가운데 통과하는 것이 없다. 판단 없이 풀리는 과제를 걸러낸다.

## 4. 채점

| 조건      | 판정 방법                                                                                                                                                    |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 동작 보존 | 원본과 제출물을 같은 입력으로 실행해 예외 여부, 반환값, 호출 뒤의 인자 상태를 비교한다. `Object.is` 기반 구조 동치를 쓰고 키 순서와 프로토타입은 보지 않는다 |
| 타입 검사 | 고정한 컴파일러 옵션으로 깨끗한 폴더에서 검사한다. `@ts-ignore` 같은 주석과 새로 들어온 `any`는 실패다                                                       |
| 번들 크기 | `esbuild`로 번들·압축한 뒤 gzip한 바이트 수가 기준 해답 × (1 + ε) 이하                                                                                       |
| 자기 코드 | 번들에서 `node_modules` 밖 코드가 차지하는 바이트가 기준 해답의 값 + 허용치 이하. 유틸리티를 직접 구현하지 않았는지 판정한다                                 |

**기준 해답**은 사람이 정하지 않는다. 함수마다 사전 등록한 후보 코드(strict, compat, 어댑터, lodash 유지)의 모든 조합을 같은 채점기에 통과시켜, 동작과 타입이 보존되는 것 중 번들이 가장 작은 조합으로 정한다. `startCase`와 `camelCase`가 함께 든 과제에서는 "동작이 같으면 strict"를 따른 조합보다 compat끼리 묶은 조합이 더 작았다. compat 함수들이 내부 코드를 공유하기 때문이다. 작성자가 정답을 적었다면 틀렸을 경우다.

**1차 지표**는 네 조건을 모두 충족하는 "요구 충족"이다. 2차 지표 "정확성"은 동작과 타입만 본다.

## 5. 분석

- **분석 단위는 과제다.** 같은 과제를 반복한 실행은 서로 독립이 아니므로 과제별 통과 비율을 먼저 낸다 (Miller, [arXiv:2411.00640](https://arxiv.org/abs/2411.00640)).
- **의도 배정 분석.** 시간·턴 한도에 걸린 실행은 0점으로 넣는다. 인프라 실패(프로세스 오류, API 오류, 인증 차단)는 같은 규칙으로 다시 실행한다. 실패 실행을 빼면 턴이 긴 쪽에서 어려운 실행만 빠져 점수가 부푼다.
- **검정.** 과제별 차이에 양측 부호 뒤집기 정확 검정을 쓴다. 표본이 작을 때 정규 근사 구간은 실제보다 좁다 (Bowyer 외, [arXiv:2503.01747](https://arxiv.org/abs/2503.01747)). 같은 검정을 SWE-Skills-Bench([arXiv:2603.15401](https://arxiv.org/abs/2603.15401))가 썼다.
- **판정 순서.** 차이 검정이 유의하면 부호로 개선·악화. 아니면 동등 조건을 모두 충족할 때만 동등. 동등 조건은 ±δ로 옮긴 두 단측 검정의 유의, 부트스트랩 구간이 ±δ 안, 대조 조건에 개선·악화의 여지가 있음이다. 그 외는 판정 불가다. 차이가 유의하지 않다는 것은 차이가 없다는 증거가 아니므로 동등은 별도 검정으로만 낸다.
- **분석 절차의 검증.** 반분 재표집으로 차이 없는 데이터에서 잘못 판정하는 비율을, 검출력 곡선으로 실제 차이가 있을 때 잡아내는 비율을 측정한다. 검출력 곡선은 대조와 처리에 서로 다른 실행을 써야 실행 간 변동이 남는다.

## 6. 실행 상태

| 상태           | 조건                                        | 분석에서                     |
| -------------- | ------------------------------------------- | ---------------------------- |
| `completed`    | 정상 종료                                   | 채점                         |
| `limit`        | 시간·턴 한도                                | 0점                          |
| `infra`        | 프로세스·API 오류, 인증 차단                | 최대 3회 재실행. 남으면 결측 |
| `harness`      | 처리 조건인데 대상 Skill이 로드 목록에 없음 | 재실행                       |
| `contaminated` | 대조 조건에 대상 Skill이 로드됨             | 실행 묶음 전체 무효          |

시험 단계에서 인증 요청이 약 4분 동안 403으로 막혀 17건이 실패했다. 이 분류가 없었다면 산출물 없는 실행이 원본 제출로 채점돼 정확성 지표에서 통과로 집계됐다.

## 7. 사전 등록

본 실행 전에 [preregistration.json](../suites/es-toolkit/migrate/preregistration.json)을 공개 리포지토리에 올리고 `prereg-migrate-v1` 태그를 달았다. 숨겨야 하는 자료(후보 코드, 생성 시드, 기준 해답)는 원문 대신 솔트를 붙인 파일별 SHA-256만 올렸다. 원문과 솔트를 공개하면 누구나 해시를 대조할 수 있다.

## 8. 한계

- 작성자가 `SKILL.md`를 읽은 뒤 함수 목록과 입력 범위를 정했다.
- 사전 등록 전에 채택한 과제를 Haiku로 한 번씩 실행해 결과를 봤다. 그 뒤 과제와 판정 규칙은 바꾸지 않았다.
- 과제는 작은 합성 파일이다. 모델은 Haiku 하나다.
- 동작 보존은 입력 범위 안의 유한한 입력으로만 확인한다.
- 기준 해답은 등록한 후보 조합 중 최소다. 다른 라이브러리 함수를 조합한 더 작은 답이 있을 수 있다(그런 답도 통과한다).
- 번들 크기는 고정한 `esbuild` 설정에서의 값이다.
- 산출물을 파일로 받으려고 모든 조건에 같은 안내 문장을 넣었다. Skill이 정한 출력 형식과 다르다.
- `placebo`는 공식 Skill의 약 절반 길이라 컨텍스트 길이를 완전히 맞추지 못했다.
- `node -e "fetch(...)"` 같은 경로는 거부 규칙으로 막지 못한다.
- 사람 감사는 아직 하지 않았다.
- `recommend`, `guide` Skill은 평가하지 않았다.
